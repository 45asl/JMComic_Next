# 工程笔记

这份文件是维护这个小应用时攒下来的**过程记录**：修过哪些真实缺陷、为什么那样修、
哪些风险有意留着没动、构建与验证时踩过的坑。

README 面向「想知道这是什么、怎么用、怎么编译」的读者；这一份面向「要改这份代码的人」——
包括几个月后的我自己。

## 一轮自查：修掉的真实缺陷

下面这些不是「顺手重构」，而是逐条对照代码与实际接口行为查出来的问题，
每一条都写清了**症状**与**为什么这样改**。修复后重新编译、装机、冷启动验证：
`setting` / `promote` / `latest` 均 200，无崩溃。

### 协议与网络层

| 问题 | 症状 | 处理 |
| --- | --- | --- |
| 解密用「响应到达时」的时间戳，而非「请求发出时」的 | 并发请求下偶发解密失败并级联重试 | 拦截器取一次时间戳，两个头同源，并钉在请求 tag 上供解密使用 |
| 先解密再判 `code`，且只认 `msg` | 密码错误提示成「解密失败/没有访问权限」，还白跑一次请求 | 先判 HTTP 状态与业务码，读 `errorMsg` |
| 403 也清登录态 | 中间设备/WAF 的 403 会把人踢下线 | 只有 401 视为凭证失效 |
| 主机一旦选中永不更换 | 随机挑中死域名后，整个进程内怎么刷新都没用 | 网络类失败标记主机可疑，下次引导重新发现 |
| 主机发现复用业务客户端 | 向第三方对象存储发出带 JWT 的请求 | 发现流程用不带任何拦截器的独立客户端 |
| 图床主机只取一次且失败被吞掉 | 一次 `setting` 抖动导致整个会话所有封面/头像空着 | 引导时若还没有图床主机就重试 |
| `total` 缺失时用「本页条数」冒充 | 分页判断 `size >= total` 在第一页即成立 → **永远停在第一页**，界面还显示「共 20 项」 | 未知就是 0（未知），到底由「本页为空」判断 |
| `AuthStore` 缓存无同步、凭证在主线程落盘 | 刚登录的请求可能读不到 token；登录成功瞬间卡顿 | 加锁保护读改写；Keystore 加解密与落盘移到 IO |

### 界面层

| 问题 | 症状 | 处理 |
| --- | --- | --- |
| 页脚失败后仍自动触发 | 断网时列表底部**无休止重试**，一句话都不说 | 抽出共用的 `LoadMoreFooter`：加载中/失败可重试/已经到底/上滑加载四种状态，且失败不再自动触发 |
| 首页续加失败写进首页错误标志 | 一次抖动后「加载更多」永久失效，且没有任何提示 | 续加错误与首屏错误分开，页脚给重试入口 |
| 收藏/历史每次返回都整屏转圈 | 深翻列表 → 进详情 → 返回，列表**闪一下并回到第一条** | 有内容时不整屏转圈（列表留在组合里），返回时静默刷新；失败保留原内容 |
| 收藏夹改名/删除后整屏转圈 | 同上，操作完列表跳回顶部 | 同上 |
| 详情页静默刷新失败会清空整页 | 从阅读页返回时网络抖一下，封面/元信息/目录全变成「加载失败」 | 只有拿到新数据才替换；失败时保留旧内容，只在什么都没有时才报错 |
| 详情页首次打开发两次相同请求 | 实测：初始请求 54.873 发出、55.281 返回，55.743 又发一次 —— 导航转场结束后才派发的 `ON_RESUME` 正好落在初始请求**之后**，在飞闸门挡不住 | 在飞闸门 + 「刚拉过就跳过」（1.5 秒窗口）；从阅读页返回这类真正的重新进入间隔远大于它。改后实测每次打开只发一次 |
| 「加载更多」的结果可能属于上一个筛选条件 | 换分类/换收藏夹/改筛选时从第一页重来，而在飞的续加请求回来后会**并进新列表**，表现为「前后内容对不上」（最难复现的一类错误） | 每个分页器加世代号，过期结果丢弃；顺手把 `loadingMore` 落下，否则新条件会被永久挡住 |
| 阅读页某页加载失败没有任何提示 | 滚动模式是一段说不清的空白（失败页高度为 0），翻页模式是一整页黑屏，且无法重试 | 加载中/失败两个占位态：滚动模式按 3:4 撑出高度，失败可点击重试（重试会换 `memoryCacheKey` 以真正重发请求） |
| 需要登录的操作只跳登录页，不说原因 | 点收藏/点赞直接落到登录页，用户不知道那次点击是没生效还是登录后会自动补上（不会，要再点一次） | 登录页新增 `reason` 参数，触发方传入「收藏需要登录」，页面上显示「登录后请再点一次刚才那个按钮」 |
| 「我的 → 服务端」把请求失败与「未提供」混为一谈 | 网络失败时读起来像一条协议事实，用户不会想到重试 | 分开显示：读取失败时给出错误文案，只有确实读到但字段为空才写「未提供」 |
| 注册/忘记密码的失败被吞掉 | 提交后按钮转一下就没反应，没有任何提示 | `submit` 不再用 `null` 覆盖 block 内部写入的错误 |
| 带标签进搜索页会重复自动搜索 | 从标签进入 → 自己改了关键词 → 进详情再返回：**输入框显示新词、列表却是旧标签的结果** | 自动搜索加一次性标记 |
| 换话失败仍推进当前话 | 屏幕上还是上一话，状态已指向下一话 → 再点「下一话」**跳过一话**并把跳过的那一话记成已读 | 只有请求成功才提交新的章节 id 与进度；失败给出提示 |
| 翻页模式下「点一下收起工具栏」是死的 | 收起后没有任何入口能再调出返回按钮与章节切换（子组件先消费了按下事件） | 点击回调传进图片自身的检测器；两种形态行为一致 |
| 阅读形态有两份状态 | 阅读页里切换后，「我的 → 阅读形态」仍显示旧选项，再点一下又把刚做的切换覆盖回去 | 与主题同样由上层托管 |
| 连点两下压出两层相同页面 | 返回一次看着像没反应 | 前进导航统一加 `launchSingleTop` |
| 章节选择器翻页后停在底部 | 新一页一打开就像内容缺了一半 | 滚动状态按页码重建 |

### 有意保留的行为（不是遗漏）

- **阅读形态切换会丢当前滚动位置**：官方也是这么做的（`Read.tsx` 切换形态时重置），
  保留位置属于改行为，不属于修缺陷。
- **空关键词点搜索**：现在给一句「请输入关键词」，而不是静默什么都不做。
- **评论仍只读**，不做发帖与投票；**图片切片与份数推导**逐条对照过源码，未发现问题。

## 已知风险与后续可做的事

这一轮自查里**没有动**的东西，以及为什么。列出来是为了让下一个人知道边界在哪，
而不是让它们悄悄消失。

| 项 | 现状 | 为什么先不动 |
| --- | --- | --- |
| 长条页的位图内存 | **已量化，不是现实风险**：实测 6 部作品 18 页，单页最大 720×3058 ≈ 8 MB，典型 1–5 MB（见〈页面尺寸实测〉），「一页 64 MB」是理论推演 | 限幅对当前数据完全空转，却会影响所有页清晰度（按宽铺满是放大显示，砍分辨率看得见）。留观察点：出现高过约 6000 px 的页再限幅 |
| `openChapter` 不取消在飞的加载 | 连续快速切话时后发者胜出（最后一次请求的结果生效） | 现状自洽（不会显示错的一话）。要改需引入取消机制，收益不明确 |
| 无 id 的评论/列表项 | `id` 默认空串，理论上重复 key 会崩 | 没有任何实测证据表明服务端会省略 id；先记着 |

## 阅读页：页与页之间不能有缝

使用者在真机上指出「漫画内图与图之间有间隔」，量出来是相邻两页 **8px = 4.0dp** ——
我给滚动列表加了 `Arrangement.spacedBy(Spacing.xs)`，还顺手给每页套了 4dp 圆角裁剪。

**这是设计理解错误，不是手滑。** 绝大多数作品是「分页拼成的伪长图」，
相邻页必须严丝合缝地接上；官方 Web 端（`Read.tsx`）的写法是：

```jsx
<div key={d.page} className="w-full relative mt-[-2px]">
```

没有间距、没有圆角，还要用 -2px 负边距让两页互相咬合 —— 用来消掉浏览器亚像素舍入留下的缝。
我这边反而加了间距与圆角，等于在每道接缝上切两刀。

同源的还有一处：加载中的占位原来会画一块灰色底，在长图里同样像一道横条。
现在只有**失败**才画底色与重试提示，加载中只占高度不画东西（图到位时也不会跳）。

**验证方式**：`uiautomator dump` 里每张图都有 `content-desc="第 N 页"` 与 bounds，
直接算「下一页的顶 − 上一页的底」即可 —— 改前 8px，改后 0px。

## 评论：真机走通之后记下的行为

发表评论这条链路是使用者本人在真机上按下第一次发送之后才验完的，过程中确认了几件事：

| 事项 | 实测结果 |
| --- | --- |
| 发表响应 | 对象 `{msg,status,aid,cid,spoiler}`，`status` 取 `"ok"`/`"fail"` |
| 删除响应 | 同样是对象：`{"msg":"评论成功删除!","status":"ok","cid":…}` |
| 内容限制 | **拒绝英文与数字** —— 含 `CTRLc` 的提交被拒（`status:"fail"` + 「抱歉，暂时不可输入英文和数字…」） |
| 删除权限 | 只对 `UID` 与当前账号一致的那条显示删除按钮（服务端也只接受本人的删除） |
| 正文形态 | 服务端把正文包了 HTML：`<div style='flex-direction:row;flex-wrap:wrap;'>…</div>`；提示里用 `<br>` |

最后一条直接导致了界面问题：Compose 里当纯文本渲染，用户看到的就是一串标签。
现在统一走 `ui/HtmlText.kt` 的 `plainText()`（`<br>` 转换行、去标签、还原实体），
并补了 5 个用实测原文写的测试。

## 响应形态：四个「不会报错、只会静默出错」的坑

这一组是用真实账号在真机上跑出来的。它们的共同点是**编译通过、测试通过、界面不报错**，
只是功能不工作或者做成反的：

| 接口 | 我以为的形态 | 实际形态 | 表现 |
| --- | --- | --- | --- |
| `album_sertracking` POST | `{status,msg}` 对象 | **一句人话** `"已追踪!"` / `"已取消追踪!"` | 被当成解密失败→触发重试→非幂等 POST 发两次→追更开了又关 |
| `album_tracking` | `{list,total}` | **`{item,totalCnt}`** | 追更列表永远显示 0 条 |
| `album_download_2/<id>` | 有 `status`，`"1"` 为成功 | **成功时没有 `status`**，只有 `title`/`fileSize`/`download_url` | 界面误报「这个作品暂时不能下载」 |
| 追更按钮的状态 | 本地取反 | 服务端文案才是权威 | 本地状态与服务器不一致时，按钮显示成相反状态 |

由此定下两条规矩（都已写进代码注释）：

1. **解密不能只认 JSON。** `data` 解出来是一句人话也是合法结果；把它当失败会让上层重试。
2. **POST 永不自动重发。** 这个服务端大量接口是「点一下改一次状态」，重发一次就是撤销用户的操作；
   发表评论被重发两次更是灾难。解不开就报错，让人决定。

## 需要登录的那几块：三个反直觉点（都已实测）

追更、标签收藏、整部下载、发表评论都要求登录，实测（未登录时打一遍）确认了三件事：

| 接口 | 反直觉之处 | 实测响应 |
| --- | --- | --- |
| `album_tracking`（追更列表） | 是 **POST**，而其它列表接口都是 GET | 未登录：HTTP 401 + `errorMsg "尚未登入"` |
| `album_download_2/<id>`（整部下载） | 未登录**不是 401**，而是 **HTTP 200** + 业务字段失败 | `{"status":"0","msg":"請先登入"}` |
| `tags_favorite`（收藏标签） | 条目的字段名是 **`tag`**，不是 `name`/`id` | 未登录：HTTP 401 + `data` 解出 `{"type":"auth_fail"}` |

前两条的后果都很实际：把 `album_tracking` 当 GET 会一直拿不到列表；把下载的失败响应当成功
会给出一个空链接、让用户以为「点了没反应」。所以这两处的判断都写在数据层而不是界面层。

另外，`album_sertracking` GET（查是否已追更）的 `data` **形态没有文档**，
未登录时是 `{"status":"fail","msg":…}`，登录后可能是布尔或对象，因此按「只有明确表示真才算真」
处理 —— 反过来（把失败当已追更）更糟：用户会以为自己早就关注了，于是再也不会去点。

## 构建相关的实测与坑

### 构建耗时：实测的瓶颈与取舍

用 `--profile` 逐任务测量后，**最大的单项开销不是 R8，而是 lint**：

| 任务 | 耗时 | 占比 |
| --- | --- | --- |
| `lintVitalAnalyzeRelease` | **55.9s** | **77%** |
| `compileReleaseKotlin` | 8.8s | 12% |
| 其余全部 | < 2s 各 | — |

因此 `app/build.gradle.kts` 里关掉了 release 的 lintVital（`lint { checkReleaseBuilds = false }`）。
**同样条件下（同类改动、均带 `--no-build-cache`）release 构建从 73 秒降到 34 秒。**

丢掉的只是一道**质量门禁**，不是构建的必要环节 —— 需要时显式运行 `gradle :app:lint` 即可，
比在每次构建里都跑一遍静态分析划算得多。

已启用的构建缓存与配置缓存（`org.gradle.configuration-cache` / `org.gradle.caching`）
让「无改动」构建降到 4 秒左右。

**顺带记录两条走过的弯路，避免以后重复尝试：**

1. **调 CPU 频率没有用。** 实测在本机（aarch64，已因发热被限频，`policy0` 上限
   1363200 而硬件上限 3532800）抬高 `scaling_min_freq` 后，固定工作量的
   4 线程 SHA256 基准为 2369/2217ms → 2000/2375ms，**差异完全落在噪声里**。
   而且 `scaling_governor` 连 root 都写不进（vendor 锁死）。
   受限的是热与内存，不是频率档位。
2. **`org.gradle.workers.max=2` 是个错误的自作聪明。** 当时以为内存紧张就该压低并行度，
   实际测下来没有任何收益，反而让构建更慢。已移除，改用默认并行度。

### 一个必须知道的环境规避：关闭 AGP 的资源优化

`gradle.properties` 里有一行看起来可有可无、实际**不能删**的设置：

```properties
android.enableResourceOptimizations=false
```

原因：在本环境（aarch64 + `aapt2FromMavenOverride` 指向 arm64 版 aapt2）下，
AGP 的 `optimizeReleaseResources` 步骤会产出**空的资源表**，后果是 release 包只剩 111 个条目：

- 没有 `AndroidManifest.xml`
- 没有 `resources.arsc`
- `apksigner verify` 报 `Missing AndroidManifest.xml`
- `pm install` 直接失败

**debug 变体不走这个步骤，因此一直正常 —— 问题只在发布包里出现**，
非常容易一路构建到「包都出来了」才发现装不上。

排查过程（逐项排除，每一步都是实测）：关闭 `isShrinkResources` → 仍缺失；
关闭 `isMinifyEnabled` → 仍缺失；移除 `packaging {}` 块 → 仍缺失；
关掉 `enableResourceOptimizations` → **立即恢复**为 1039 个条目并含 manifest 与 `resources.arsc`。

代价是不再做资源的无用条目裁剪，体积略大 —— 换一个装得上的发布包，值得。

## 单元测试：钉住「改坏了也不会报错」的那几处

`app/src/test/` 下有 17 个纯 JVM 测试（`gradle :app:testDebugUnitTest`，约 0.2 秒），
只覆盖不需要设备的部分：

- **切片份数推导**：期望值不是照 Kotlin 实现反推，而是用官方还原源码里的 `get_num`
  在 Node 里算出来的向量（含三段 aid 区间的边界：`268850`、`421925`、`421926`，
  以及 `aid < 268850` 时「不取模也匹配不到 case、份数保持 10」这条反直觉分支）。
- **份数恒为正偶数**（2..20），下游 `h % num` 因此不可能除零。
- **md5 / Token 推导**：`Token` 头同时就是响应 AES 密钥，两者必须逐字节相同。
- **解析容错**：`id` 时数字时字符串、`update_at` 时数字时字符串、
  `author` 是数组或逗号串、`category_sub.id` 为 null、评论的大写短名 `CID`/`UID`/`AID`、
  失败的文案在 `errorMsg` 而不是 `msg`。

还有两条是**回归测试**，钉住这一轮修掉的坑：
总数缺失时不许用「本页条数」冒充（否则分页永远停在第一页）；
连载更新末页的 `{"error":"没有资料"}` 必须解析成空列表而不是失败。

验证过测试确实有牙齿：把 `sliceCount` 里 `0 -> 2` 改成 `0 -> 4`，
`slice count matches the official get_num` 立刻失败；改回来即恢复。

## 怎么验证「网络出问题时会怎样」

失败路径（某页图片挂了、列表续加失败、首屏加载失败）是最容易写错、也最难测的一类。
真机验证的做法：

1. 起一个**选择性失败**的代理（`scripts/flaky_cdn_proxy.py`）：命中名单的主机直接断开，
   其余正常转发 —— 于是可以做到「API 通、图床断」，正好是「图片挂了但页面还能用」那种情况。
2. 用 `adb reverse tcp:8888 tcp:8888` 把设备端口反向转发到本机（绕开局域网可达性 ——
   这台测试设备 TCP 连不到本机，ICMP 却通），然后把设备的系统代理指到 `127.0.0.1:8888`。
3. `uiautomator dump` 把界面读成文本，于是「页脚显示什么」「失败占位有没有出现」都能断言 ——
   这台设备（Android 12）能 dump，而小米那台会报 `could not get idle state`。

这一轮实测到的行为（都是在这一套下面跑出来的）：

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 冷启动时断网 | 首屏给出错误 + 重试 | 「无法连接到服务端：主机发现全部失败」+「重试」 |
| 列表续加失败 | 只试一次，页脚可点重试 | 页脚「加载失败，点击重试」，代理日志里**只有 1 次**被拦 |
| 点续加的重试 | 从**下一页**继续，不从头再来 | `serialization?…&page=2` |
| 阅读页某页图片失败 | 该页出占位且可点重试 | 「这一页加载失败 · 点击重试」（每页各自计次，点一个恢复一个） |
| 列表到底 | 明确收尾 | 「已经到底了」 |

## 页面尺寸实测（决定要不要给解码限幅）

「长条页会不会撑爆内存」这个问题争论不出结果，得看数据。实测方法是拉取多部作品的
`comic_read`，挑首页/中间/末页下载前 512 KB，从图片头读出真实像素尺寸（WebP 的
`VP8 `/`VP8L`/`VP8X` 三种都解析）：

| 作品 | 页数 | 取样页尺寸 | 解码 ARGB_8888 |
| --- | --- | --- | --- |
| 1117807 | 277 | 720×500 / 720×700 / 720×608 | ≤ 1 MB |
| 19 | 210 | 960×1371 / 960×1496 / 960×1420 | ≈ 5 MB |
| 1217170 | 54 | 720×3008 / 720×3058 / 720×127 | ≤ 8 MB |
| 1473604 | 158 | 720×500 / 720×700 / 720×263 | ≤ 1 MB |
| 1080582 | 140 | 960×1464 / 960×1464 / 960×836 | ≈ 5 MB |
| 1195659 | 314 | 720×500 / 720×700 / 720×26 | ≤ 1 MB |

**结论：这批采样里单页最大 720×3058 ≈ 8 MB，典型 1–5 MB。**图片宽度只有 720 或 960
（服务端生成的是定宽切片），高度随画面变化但没见到上万像素的极端长条 ——
也就是说「一页 64 MB」是理论推演，不是这台 CDN 的实际形态。

因此**本轮没有改解码尺寸**：限幅对当前数据完全是空转，却会影响所有页的清晰度
（按宽铺满后是放大显示，砍分辨率是看得见的损失）。真正该做的动作是
**留一个量化过的观察点**：如果哪天出现高过约 6000 px 的页，再考虑
`.size(宽, 上限高)` + `precision(INEXACT)` 这种等比缩小（不变形）。

顺带两条核实过的结论，省得下次重新验：
- **`allowRgb565` 在这里无效**：Coil 3 只要请求上挂了 `Transformation`，就要求位图配置
  属于 `VALID_TRANSFORMATION_CONFIGS`（`ARGB_8888` / `RGBA_F16`），会强制替换回 ARGB_8888。
  同一个机制也解释了为什么这里不会出现「硬件位图不能绘制」的崩溃。
- **磁盘缓存里存的是未还原的原始字节**，转换结果只在内存缓存里 ——
  每次冷启动后第一次看到某页仍要重新解码 + 还原。

## 内容屏蔽：为什么过滤放在数据层，以及标签为什么只能在详情页生效

参考项目 [haka_comic](https://github.com/raoxwup/haka_comic) 用两张 SQLite 表
（`tag_block` / `word_block`）加 Provider 通知，在**每个列表页面里**各自过滤。本项目的做法不同，
原因是这里的列表出口比它多，而且分散：

| 出口 | 接口 |
| --- | --- |
| 首页推荐分区 / 最新上架 | `promote` / `latest` |
| 分区更多 / 连载更新表 | `promote_list` / `serialization` |
| 搜索 | `search` |
| 分类 | `categories` 过滤档 |
| 收藏 / 历史 / 追更 | `favorite` / `watch_list` / `album_tracking` |
| 随机推荐 | `promote` 随机挑一个分区 |

七个出口如果在页面层各写一遍过滤，**漏一个不会报错，只会让人觉得「屏蔽有时候不灵」** ——
这类缺陷很难被发现，更难被复现。所以全部收敛到 `JmRepository` 的私有扩展函数
`PagedList.blockFiltered()`，页面拿到的就已经是过滤后的结果。

`hidden` 计数随之带上（`PagedList.hidden`）：过滤之后「本页 30 条里被藏了 3 条」这件事必须可解释，
否则用户看到「总数 120、翻两页就到底」只会认为是 bug。空规则时整个过滤路径直接短路（`BlockRules.isEmpty`），
不产生额外开销。

**标签规则为什么改在详情页。** 实测所有列表接口的载荷字段只有
`id/name/author/image/category/category_sub/update_at/is_favorite/liked`，
**没有 `tags`**（`tags` 只在 `album` 详情响应的 `data` 里）。也就是说列表层根本没有标签可匹配，
参考项目能按标签过滤是因为它的数据源带标签。硬做一个「猜标签」的近似（比如拿标题当标签）
会制造出无法解释的隐藏，不如把规则放到真正拿得到标签的地方：

- 打开作品时若命中标签 → 顶部提示条「含已屏蔽标签：xxx」+ 「不再屏蔽」
- 详情页的标签与作者支持**长按屏蔽**（`combinedClickable`），省掉回设置页手输一遍

**长按 vs. 弹菜单**：长按是这里唯一不占版面的入口（标签行本身已经很密），
代价是**不可发现** —— 所以标签行下面写了一句「标签：点开搜索，长按屏蔽」，
设置页的说明栏也把三类规则的生效范围逐条写出来。可发现性靠文案补，而不是靠再加一个按钮。

**名单存储**：SharedPreferences + JSON 数组（`jm_block`），与 `AppPrefs` / `ReadProgressStore` 同一套路。
条目是人手加的（几十条量级），不需要数据库；`BlockRules` 暴露成 `StateFlow`，
这样在设置页里改了名单，已经打开的列表页能立刻重新过滤。

**许可边界**：haka_comic 是 GPL-3.0 的 Flutter 项目，本项目是 MIT 的 Kotlin 项目。
参考的是功能设计（三类规则、命中即隐藏、2~20 字符校验、详情页快捷屏蔽），没有使用其代码；
若将来真要引入它的代码（GPL-3.0 有传染性），必须先把本项目整体改为 GPL-3.0。README 的
〈许可〉一节写了这条，这里只记「为什么当时这么判断」。

### 屏蔽功能的真机验证（A/B，而不是「看着像生效了」）

屏蔽是那种「规则没生效也看不出来」的功能：列表少几条和分页到底长得一模一样。
所以验证方式是在**同一个关键词、同一个会话里**改规则再看结果 —— 只有 A/B 才能排除
「这个查询本来就查不到东西」这种解释。

| # | 生效规则 | 搜索 `C108` | 结论 |
| --- | --- | --- | --- |
| A | 关键词 `C108` | 没有找到相关作品 | 关键词规则在列表层生效 |
| B | 无 | 3 条（分类都是「同人」） | 排除「查询本身没结果」 |
| C | 分类 `同人` | 没有找到相关作品 | 分类规则在列表层生效 |
| D | 无（在界面上删掉该条） | 3 条 | 删除规则后立刻恢复 |

另外逐条验过的：重复添加（`c108` 与 `C108` 视为同一条）、长度上限下限（1 个字符被拒）、
详情页长按标签屏蔽 → 顶部提示条「按你的屏蔽规则：含「韩漫」」→ 「不再屏蔽」后提示条消失。

**中文规则怎么写进去的。** 设备上只有搜狗输入法，`adb shell input text` 打不了中文
（会走拼音组词），也打不了下划线。分类/标签这类中文规则改用
`run-as <pkg> sh -c 'cat > shared_prefs/jm_block.xml'` 直接写入（debug 包可 run-as），
先 `am force-stop` 再启动让它从磁盘读 —— 界面上的读取路径与手动添加完全一致，
所以这样注入的中文规则在控件树里能看到「分类屏蔽 · 1 条」和「同人」芯片。

### 维护这台测试机时的三个坑（都写进了 `scripts/ui_probe.py`）

1. **屏幕会自己转。** 自动旋转开着，同一次操作里两次 `uiautomator dump` 可能一次横屏一次竖屏，
   写死坐标会点空（我为此白跑了好几轮）。脚本改成每次都从**刚 dump 出来的控件树**里取 bounds。
2. **底部导航的文字节点 bounds 是 `[0,0][0,0]`**（Compose 的 `NavigationBar` 就是这样导出的），
   按文本点 Tab 永远点不到；改成按屏幕宽度切片定位，并且当前选中的 Tab 不可点（可点区域常常只有 3 个），
   所以按「第几格」而不是「第几个可点区域」来数。
3. **软键盘会盖住底部导航。** 输入框有焦点时点底部会打在键盘上（有一次把搜索词删掉一个字符，
   还有一次直接点到 `x` 键上）。操作前先 `input keyevent 4` 收键盘，或者用 `dumpsys window | grep ITYPE_IME` 确认。

## 四套主题风格：怎么保证它们真的是四套

「做了四个选项但看起来差不多」是这类功能最常见的失败方式，而且**代码是能跑通的** ——
没有崩溃、没有报错，只是白做。所以这次的验收标准不是「能切换」，而是**能量出差别**。

### 收口在 GlassSurface

四套风格要在 13 个界面文件、几十处调用上同时生效，靠的是**一个收口**：
所有卡片/浮层都走 `GlassSurface`，它按 `JmSpec.surface.craft` 分支（Acrylic / Glass / Card / Tonal）。
页面完全不知道自己跑在哪套风格下 —— 否则每加一个页面就得记得处理四种风格，迟早漏。

圆角与投影同理：`Radius.*` 与 `Elevation.*` 从 `@Composable` 的取值改成读 `LocalJmSpec`，
24 处调用点一行都不用改。这是把「风格」做成令牌而不是做成 `if (style == ...)` 的收益。

### 预览必须用真令牌渲染

设置页的四张预览卡是把 `LocalJmPalette` / `LocalJmSpec` **临时替换成目标风格**再渲染真实的
`GlassSurface`。画一张示意图（自绘色块）也能做，但那种图会跟实现走散：改了 GlassSurface，
示意图不会跟着变，于是它开始撒谎 —— 而且没人会发现。共用绘制代码的预览不会。

### 没长眼睛的 agent 怎么验收视觉

这个环境里我看不到截图（模型不吃图），所以验收改成**量像素**：`scripts/px_probe.py`
把 `screencap` 拉回来的 PNG 转成原始 RGB（本机有 ImageMagick，比纯 Python 解码省事），
然后在 uiautomator 给出的控件 bounds 上做四件事：

1. **填充色 vs 背景色的距离** —— 实心风格（Miuix/Material）这个距离应该很大，
   玻璃风格（WindowGlass/Translucent）应该明显更小，Translucent 又比 WindowGlass 更小；
2. **描边证据** —— 横穿卡片左边界扫一行像素，若存在既不像背景也不像填充的一列，就说明有描边；
   Miuix/Material 这一项必须接近 0；
3. **圆角半径** —— 比较「角落列」与「中部列」上顶边的 y 值，差值即半径，
   应当是 WindowGlass 8dp≈16px、Miuix 20dp≈40px（320dpi 下 1dp = 2px）；
4. **壁纸是否真的透过来** —— 换一张花壁纸后，玻璃风格的填充色会随之变化，实心风格几乎不变。

这套办法同样适用于以后任何「改版前后有没有变」的问题，比截图肉眼比对更可靠：
数字不会因为我觉得「看起来差不多」而放过一处没生效的改动。

### 顺手抓到的一个真问题：薄层画在了内容之上

`GlassSurface` 原来的实现里，MIUI 橙→蓝薄层与上缘高光是 `drawWithContent { drawContent(); drawRect(...) }` ——
**画在内容之上**，等于给玻璃上的文字蒙了一层色。原来的薄层是 20% 透明度的橙/蓝，看不出来；
这次 Translucent 要铺 12% 的**实心强调色**，会直接把文字糊掉。改成 `drawBehind` 后，
材质层都在内容之下，文字始终干净。这种问题不靠「看」是发现不了的，靠的是重读一层层的绘制顺序。

### 壁纸与第三方请求的纪律

五个来源里默认是「纯渐变」，一个字节都不发 —— 与博客不同（博客默认 Bing），
理由是这里是阅读器，不该在用户没要求时连出去。开启了之后也照博客的做法克制：
地址缓存在本地轮换（攒够 4 张就不再请求）、Bing 每天只重新取一次、手动连点有冷却。

## 四套界面风格：怎么做到「真的不一样」，以及怎么在没有眼睛的情况下验收

### 收口在 GlassSurface

四套风格要同时作用于 13 个界面文件、几十处调用，靠的是一个收口：所有卡片/浮层都走
`GlassSurface`，它按 `JmSpec.surface.craft` 分支（Acrylic / Glass / Card / Tonal）。

`@Composable` 取值，24 处调用点一行都不用改；`RoundedCornerShape(Radius.xx)` 统一换成
`jmShape(Radius.xx)`，于是「Miuix 用连续圆角」也只是这一个函数里的一次判断。

### 参考来源（都不是我编的）

| 风格 | 依据 | 数值来源 |
| --- | --- | --- |
| WindowGlass | Windows 11 窗口玻璃 | Fluent 规范：窗口圆角 8px、控件 4px；Acrylic 的模糊/噪点沿用博客令牌 |
| Translucent | Windhawk 的 Translucent 系列 | 那一族**没有**数值化的不透明度与模糊（源码里 `grep -i opacity` 零命中），透明度只体现在渐变的 alpha 上；所以这里的 0.58×/64dp 是按「与 WindowGlass 明显不同且能读」定的，不是抄的 |
| Miuix | HyperOS / MIUI | 小米开发文档：小组件圆角 1080p 下 38px=12.67dp、2k 下 50px=14.48dp；Miuix 组件库卡片/按钮 16dp → 取 16dp。连续圆角（平滑圆角）也是那边的概念 |
| Material | Material 3 / haka_comic | M3 圆角阶梯 4/8/12/16/28；haka_comic 的卡片一律 `elevation: 0`、圆角 8~12、AppBar `scrolledUnderElevation: 0` → 因此这个风格**不投影、不描边、不铺薄层** |

### 没长眼睛的 agent 怎么验收视觉

这个环境里我看不到截图（模型不吃图），所以验收改成**量像素**：
`scripts/px_probe.py` 把 `screencap` 拉回来的 PNG 转成原始 RGB（本机有 ImageMagick），
`scripts/verify_styles.py` 自己定位「我的 → 外观」里那四张预览卡内部的迷你场景，
`scripts/verify_cards.py` 量页面级大卡片。

量出来的结论（深色主题，320dpi）：

| 风格 | 卡片填充实测 | 与声明值距离 | 与 alpha 合成值距离 | 左边缘异常像素 |
| --- | --- | --- | --- | --- |
| WindowGlass | #1E222A | 12.7 | **0.8** | 24 → 有描边 |
| Translucent | #121521 | 32.5 | 9.0 | 24 → 有描边 |
| Miuix | #242426 | **0.0** | — | 0 → 无描边 |
| Material | #22262D | **0.0** | — | 0 → 无描边 |

第二、三列是关键：玻璃风格的填充**正好等于「声明色按 alpha 合成到背景上」的结果**
（WindowGlass 差 0.8），实心风格**正好等于声明值**（差 0.0）。
壁纸打开时更直观：Miuix / Material 的卡片填充是固定值，玻璃风格的填充随壁纸变化。

**没量成的部分，也记下来。** 圆角半径在真机上没量准：玻璃风格的填充本来就贴着背景色
（边界找不到 —— 这本身又是它透明的证据），照片壁纸下背景横向不均匀，
而半透明风格的抗锯齿与发丝描边又会让「看起来的顶边」提前。
所以圆角相关的结论改成用单元测试钉：`SquircleShapeTest` 测几何
（圆弧对角内缩 0.293r、超椭圆 n=5 是 0.129r），`ThemeStyleTest` 测令牌
（8dp / 12dp / 16dp）。**能被数学钉住的就别去数像素**，这是这轮最实在的一条经验。

## 1.3.1：Bing 尺寸段改写

### 先验证「它真的有用」，再动手

改尺寸段这件事听起来像是把横图拉成竖图（那就只是变形，反而更糟）。所以先量：
请求 `_1080x1920.jpg` 拿回来 `identify` 报 `1080x1920`，请求 `_1920x1080.jpg` 报 `1920x1080`
—— 是**裁剪**，不是缩放。确认后才写代码。

### 一个由测试抓住的坑：注释与代码不一致

第一版写成 `Regex(...).replace(url) { ... }`，注释里却写着「只在能匹配时改写，其余原样返回」。
但 `Regex.replace` 的语义是**替换全部匹配**，不是第一处。于是
`.../th?id=a_1920x1080.jpg&u=b_640x480.jpg` 会被改成两段都是 `1080x1920` —— 后一段是别人的
参数，改坏就整张图加载失败。单测 `only the first size segment is rewritten` 直接把它钉住了。

修法不是 `replaceFirst`（Kotlin 那个重载只接受 String 替换式、没有 lambda 版本），
而是 `find` + 手工拼接前后缀，这样「保留原扩展名、其余一个字符都不动」是明写的。
这条测试值得留着：它记的是一个**注释与代码不一致**的真 bug，而不是构造出来的边界。

## 1.3.2：连续圆角画反了两个角 —— 一次「测试全绿但东西是坏的」

### 症状

1.3.0 发出去之后，Miuix 风格的圆角明显不对：**右上与左下两个角像被切掉一块**
（另外两个角正常）。因为是「两个对角坏、两个对角好」，看起来不像渲染问题，像形状画错了。

### 原因

`SquircleShape.createOutline` 里，四个角都调用同一个 `quarter()`，它固定按 `θ: 0 → π/2` 采样。
问题是：**四个角里只有两个的「进入点」正好对应 θ=0**。对右上与左下来说，θ=0 是角的**出口**，
于是那两个角从出口扫回入口 —— 轮廓自交。

自交在填充上会怎样，取决于填充规则。Compose 的 `Path` 默认是 **NonZero（非零环绕）**，
反向的那一圈把绕数抵消掉了，所以那两个角不是「多出一块尖刺」，而是**少填一块**：

| 与理想平滑轮廓对比 | 差多少 | 分布 |
| --- | --- | --- |
| 修复前 | 11338px（**9.46%** 面积） | 右上 3971px、左下 4056px，另两角各约 20px |
| 修复后 | 62px（**0.05%**） | 四个角均匀分布，即采样步长的正常逼近误差 |

（栅格化验证：非零环绕填充，半径 32dp、放大 3 倍。修复后剩下的 0.05% 是 12 段 vs 400 段基准的差。）

### 为什么原来的测试没拦住

`SquircleShapeTest` 里有四条测试，全都测 `superellipseUnit` 这个纯数学函数：
`|x|^n + |y|^n = 1`、对角内缩 0.293r vs 0.129r、指数单调性。
**反向扫出来的点，依然精确落在同一条超椭圆上** —— 它们没有一个是错的，
错的是「这些点的连接顺序」。测试测的是点集，bug 出在序列上。
所以四条全绿，角却是坏的。

### 修法与教训

1. **把「顺序」变成可以断言的东西**：轮廓点从「直接往 `Path` 上画」改成返回
   `List<Offset>`（纯函数 `superellipseRoundRect`）。于是可以断言：
   - **凸性**：连续三点的叉积必须同号。反向扫 = 自交 = 出现反号
     （实测修复前 53 个叉积里 24 个反号）。这一条在旧代码上确实失败过，我验证过。
   - 四个角**都**要满足对角伸展 1.741r（只测一个角的话，另外三个画反了照样过）。
   - 闭合性与不越界。
2. **参数化要表达意图，而不是让调用方「记得」**：`quarter(cx, cy, sx, sy)` 的参数里
   没有任何东西说明「从哪个端点进」。现在改成 `corner(..., entryTurns, exitTurns)`，
   每个角把进出端点显式写出来，注释里标了 θ=0 / θ=π/2 各自落在哪条轴、哪个方向。
3. **教训一句话**：测了「每个点都对」，不等于「这些点连起来是对的」。
   凡是生成序列/路径/顺序的代码，断言要落在**相邻关系**上（凸性、连续性、闭合、单调），
   而不是只落在单个元素的性质上。

### 顺带说明：这次也没有真机验证

设备（`192.168.5.11:5555`）不在线，所以这次同样没有装机看。替代办法是**把路径栅格化**：
用同样的非零环绕规则把修复前/后的轮廓渲染成像素，与 400 段采样的「理想轮廓」逐像素比。
这个办法能量出「差 9.46% 面积、集中在哪两个角」，比肉眼看更准；
它的局限是量不到真实 Compose 渲染的细节（抗锯齿、clip 的混合方式）。

## 1.3.3：玻璃为什么看着怪 —— 一层 15 级的灰膜，和一个从没生效过的令牌

使用者的原话是「你不感觉这个玻璃很奇怪吗，看起来好怪」。这类反馈最容易被处理成
「凭感觉调几个数」，所以先把「怪」拆成可测的东西。

### 一、颗粒层其实是一层灰膜

Acrylic 的颗粒层是一张 64×64 的噪点贴图（均值 127/255），用**默认的 SrcOver** 画上去。
问题是：SrcOver 叠一层均值中灰的半透明贴图，等于把底下的颜色**往中灰拉**。

| 底 | 表面被偏移 | 卡片饱和度 | 它本该提供的颗粒 |
| --- | --- | --- | --- |
| 深色（0.10） | **+12.8 级** | 0.392 → **0.266** | ±3.1 级 |
| 近白（0.97） | **−15.1 级** | — | ±3.1 级 |

**灰膜的幅度是颗粒的 5 倍。** 也就是说这一层的主要视觉效果不是「玻璃的颗粒」，
而是「给每块玻璃蒙一层灰」—— 深色卡被提亮 13 级（几乎是原亮度的两倍）、
浅色卡被压暗 15 级，深色卡的饱和度掉了 32%。这就是「发灰、发脏」的量化版本。

**为什么不能靠调小不透明度修。** SrcOver 的偏移量是 `alpha × (0.5 − 底)`：
要把偏移压到 1 级以内，alpha 得小到约 1%，那时的颗粒只有 ±0.2 级 —— 等于把颗粒一起去掉。
偏移与幅度在这个合成方式下是**同一件事**，只能换合成方式。

改用 **Overlay**（中点灰 = 恒等变换）后：均值偏移 **0.00 级**，饱和度回到 0.392，
颗粒保留在 ±1.4 级（深色卡）。Overlay 的响应随底色的 `b(1−b)` 走，
所以近白底上的颗粒天然更弱（±0.2 级）—— 这是这套混合的代价，如实写在代码注释里。

另外把颗粒**与「用户有没有开壁纸」绑定**：底是平滑渐变时颗粒没有可散射的细节，
画上去只是脏；而且 64px 贴图在 2.75 倍密度下是约 23dp 的周期，眼睛看得出重复。

### 二、模糊令牌是死值

`SurfaceSpec.blur` 声明了 WindowGlass 40dp、Translucent 64dp，
**用 `grep` 找它的读取方：零命中。** 全应用唯一的模糊是用户在壁纸设置里手调的
`wall.blur`（默认 0）。也就是说那两套「玻璃」其实一点模糊都没做，
文档里写的 `backdrop-filter: blur(40px) saturate(165%)` 只搬来了**前面半句的数值**。

同类问题还有一个：`Glass.SATURATION = 1.65` 的注释直接写着「保留数值用于文档与后续滤镜实现」，
即**明确记录了没实现**。这次一起接上（`ColorFilter.colorMatrix(setToSaturation)`）。

**教训**：令牌里写了值，不等于它生效。测试因此不写成「声明了 > 0」，
而是断言它落在**真正被消费的那个字段**上（`backdropBlur`，由 `AmbientBackdrop` 读取）——
只断言「声明了」是拦不住死令牌的，这正是它活了两个版本的原因。

### 三、顺带修的两处

- **按压缩放只缩了内容**：`graphicsLayer { scale }` 放在 `.background()` / `.border()` **之内**，
  graphicsLayer 只包住更内层的内容，所以是「卡片不动、字在缩」。移到最外层。
- **实心风格的底铺着彩色雾**：环境底那三团径向光晕是 Acrylic 的做法，
  但 Material / Miuix 也照画 —— 于是 M3 的「平色 surface 底」变成一片紫色雾。
  新增 `backdropGlow` 令牌（Material / Miuix = 0）。

### 四、Material 从「抄 haka_comic」改成「按 M3 规范」

之前的 Material 是：把博客的玻璃色板换成几档蓝色 + 照抄 haka_comic 的表面用法
（卡片一律 elevation 0、不铺 surfaceTint）。**那是那个应用的风格化选择，不是 M3。**
改成 M3 本身之后：
颜色角色直接映射（`primary` / `surfaceContainerLow…High` / `outlineVariant` / `onSurface`…），
动态取色从「只换强调色」变成「整份配色来自系统壁纸」，
形状用 4/8/12/16/28、卡片 medium(12dp)、浮层按 elevation level 投影。

**一个可测的正确性检查**：浅色下 `primary`(#6750A4) 压 `primaryContainer`(#EADDFF) 是 5.0:1、
深色下 5.4:1，都过 WCAG AA 小字门槛 —— 所以「chip 用 accent 文字 + accentSoft 底」
这套现有写法在 Material 下依然成立，不需要为它加特例。这个数是算出来的，不是估的。

### 五、这轮的可复用经验

1. **「看起来怪」通常能翻译成「某个通道偏了多少级」。** 把材质逐层合成算一遍，
   比反复调参数快，也能防止下次再犯。
2. **混合模式是材质的一部分。** 均值非零的贴图配 SrcOver，得到的一定是「洗掉一层」，
   而不是纹理。噪声/颗粒这类效果必须用中点恒等的混合模式。
3. **令牌要断言到消费端。** 声明与生效是两件事；`grep` 一个字段的读取方，
   是发现「装饰性代码」最便宜的办法。

## 1.4.0：五个可选项，以及「验证方式本身」的一次升级

### 这次终于有真机了

1.3.1 / 1.3.2 / 1.3.3 三轮都只能靠栅格化与像素推算（测试设备离线）。这一轮设备回来了，
于是所有视觉结论都改成**在真机上量**：Android 12、720×1612、密度 2.0×。

做法：`setpref.sh` 直接写应用的 `shared_prefs`（root），比在设置页里 `input tap` 猜坐标可靠得多，
也避免分辨率变化导致脚本失效。

**踩到的第一个坑**：第一次用 shell `printf` 拼 XML，属性值的引号被 shell 吃掉了，
写出 `name=floating_bottom_bar value=true` 这种非法 XML。而 SharedPreferences 解析失败会
**静默回落到默认值** —— 表现是「改了没反应」，跟「功能没实现」一模一样。
两张截图逐像素比对完全一致（差异 0.0）才暴露出来。改成「本地生成合法 XML → push → su 落地」
后正常。**教训：配置类改动一定要有一个「确认它真的读到了」的检查**，不能只看「进程没崩」。

### 量到的四个数

| 功能 | 量什么 | 结果 |
| --- | --- | --- |
| 悬浮底栏 | 胶囊左右留白 / 高度 / 顶行宽度 | 32px = **16.0dp** / 62dp / 619px vs 最宽 655px（有圆角） |
| 通透模式 | 胶囊内部与紧邻外侧的色差 | **25.2 → 1.7** |
| 通透模式的文字处理 | 底栏标签区最暗像素 | **81 → 35**（阴影出现），对比跨度 104 → 150 |
| 莫奈套用到模糊 | 背景色相位移 | 下方光斑 Δ(+49,+32,+17)、中部 Δ(+21,+24,+23) |

### 通透模式：填充与染色要一起关

第一版只把**填充**压到 8%，量出来通透度只从 25.5 降到 16.6 —— 不够。
原因是有两层东西并不随填充缩放：强调色薄染与 MIUI 橙蓝薄层。它们同样是「盖在底色上的一层」，
所以通透模式下必须一起关掉。改完是 1.7。

**一条可复用的判断**：做「更透」这类需求时，要沿着绘制顺序把所有**不透明的层**数一遍，
只调其中一层往往会得到「改了但没效果」的结果。

### 莫奈染色：强度是量出来的

第一版给整屏染色 34/22/30%，实测把**整屏平均亮度抬了 15.3 级** —— 卡片与文字的对比
一起被冲掉。降到 16/10/14% 后是 11.0 级，色相位移仍然明显。
存在感主要交给那三团改成系统色相的光斑（它们只换色相、不改透明度，不额外提亮）。

### 预测性返回的注册顺序

`OnBackPressedDispatcher` **按后加入优先**派发。而 NavHost 组合时会注册自己的返回回调 ——
所以 `PredictiveBackHandler` 必须写在 NavHost **之后**。写在前面（直觉上更「外层」的位置）
会被 NavHost 的回调盖掉，手势永远轮不到这里，而且**不会有任何报错**。

另一件如实记录的事：这项功能**没能在真机上验证**。它是 Android 13（API 33）起的能力，
而测试机是 Android 12（API 31）。代码与 Manifest 开关都在，但没有跑过。
把它做成默认关闭的可选项，也正因为这一点。

### 动效：从「没配」到「有性格」

以前整屏一个转场都没配（用的是导航库默认淡入）。补上之后顺带把「动效性格」抽成一维：
标准 / Plasma。Plasma 取 Qt 的 `QEasingCurve`（`OutCubic` 进、`InCubic` 出）与
Kirigami 的时长（200/400ms）。

关键设计：**弹性属于风格，不属于动效性格**。HyperOS 的按下回弹是 spring，
如果被 Plasma 的 tween 覆盖掉，用户选 Plasma 就等于把 Miuix 的手感弄丢了。
所以 `asPlasma()` 只换时长、曲线、位移，`springy` 原样带过去 —— 这一条有单元测试钉住。

## 1.4.1：阅读页的五条反馈，以及「症状与病因不是一回事」

用户给了五条，其中两条的症状都很容易被误诊。记下来。

### 「拉到没加载完的图会被弹回去」——不是手势，是高度

第一反应是去找 snap / 回弹动画。**grep 了整个阅读页：没有任何 scrollTo / snap 调用。**
真正的病因是：服务端返回的图片列表里**没有尺寸**（`ReadImage` 只有 `image` 与 `page`），
所以加载中的占位只能猜一个比例；猜错时，图加载完成的那一刻条目高度变化，
整条 `LazyColumn` 跟着跳一下 —— 用户正在读的位置就被「弹」走了。

两条正交的修法，缺一不可：

1. **让占位尽量等于真实高度**（`PageRatioMemory`）：按 URL 记 + 按作品记。
   按作品那一层是关键 —— 同一部作品页面尺寸基本一致，所以第一页实测出来之后，
   后面**还没加载**的页就能直接用这个比例占位。
2. **让大多数页根本不出现在占位状态**（预取）：提前把当前页前后的一段发出去。

顺带一条**接口一致性**的约束：预取必须用与显示**完全一样**的请求。
Coil 的缓存键由请求决定，预取时少一个转换（比如反切片），存下的就是另一份东西，
用户滚到时仍要重新下载 —— 预取等于白做却看不出来。所以请求构造抽成了一个函数
（`readerImageRequest`），两边共用。

### 「阅读页 UI 与设置不同步」——是两处硬编码

翻页模式的背景写死 `Color.Black`，滚动模式取 `c.backdrop.first()`（一个平色）。
两者都不随风格/深浅/莫奈变化。改成与设置页**共用一段绘制**（`Modifier.ambientBase()`）。

这里有一条必须同时守住的约束：阅读页的底**必须不透明**，否则壁纸会从页间透出来、
伪长图的接缝重新可见（1.1.5 修的就是这个）。所以 `ambientBase()` 只画实色渐变与光斑，
不引入任何透明度依赖 —— 复用与「不能透明」这两件事因此不冲突。

### 底栏参考官方，但**不照抄色值**

官方 `ReadNav.tsx` 是 `bg-nbk bg-opacity-90` 的近黑实色。照抄色值就会重新制造
上一节那个「不同步」问题，所以只抄**结构**（两行：滑块行 + 五个动作），
颜色仍走 `GlassSurface`。**参考的是组织方式，不是像素值** —— 这两件事在移植设计时很容易混。

### 悬浮版为什么要单独设计

贴底版有整屏宽度，五个「图标 + 文字」放得下；悬浮版左右各让出 12dp 之后，
五个文字标签会挤成一条。所以悬浮版的动作用**只留图标**，把页码滑块单独提为上行。
「把贴底那条缩窄」得到的不是悬浮版，是一个更挤的贴底版。

### 又一次「证据比直觉可靠」

这台虚拟机（Android 9）的 `uiautomator dump` 会偶发失败，我 pull 到过旧文件，
一度以为「返回键坏了」。改用截图逐像素比对才确认返回正常（返回后与首页差 0.014）。
这轮同理：底栏、首屏留白、背景色**全部用 bounds 与像素数值确认**，而不是看描述。
